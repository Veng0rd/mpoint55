# Аудит функционального паритета каталога

## Состояние до исправления

- Статический preview загружал сохранённые страницы, но `MPOINT_PREVIEW.filter` учитывал только производителя. Все исходные поля `val*` визуально оставались в форме, но не влияли на товары.
- Поиск всегда открывал `/c/mototehnika/motocikly` и скрывал несовпадения только на этой странице. Остальные захваченные категории не участвовали в поиске.
- Сортировки `1` и `4` подставляли отсутствующую цену как большое число. Из-за этого товары «Уточняйте цену» попадали в начало при сортировке по убыванию.
- Сортировка `3` не имела отдельной логики. В snapshot нет достоверной даты товара, поэтому единственный честный эквивалент — исходный порядок карточек.
- Производитель сопоставлялся через вхождение полного текста option в карточку. Значение `VMC (Vento)` поэтому не совпадало с товарами `VMC`.

## Что сохранено в исходных формах

Исходный JS отправлял форму целиком (`filter_form`, включая `manuf`, `sortby` и присутствующие `val*`). Сохранённые страницы подтверждают такие поля:

| Категория | Поля характеристик |
| --- | --- |
| Мотоциклы | `val1_from/to` — Кубатура; `val2` — Тип |
| Аккумуляторы | `val1_from/to` — ёмкость; `val2_from/to` — пусковой ток; `val3` — полярность; `val4` — тип корпуса |
| Мопеды и скутеры | `val1` — тип; `val2` — модель |
| Мотошлемы | `val1` — тип; `val2` — размер |
| Мотошины | `val1` — тип; `val2` — ширина; `val3` — профиль; `val4` — диаметр |
| Мотозапчасти | `val1` — тип запчасти |
| Смазочные материалы и мотохимия | `val1` — тип |
| Техника под заказ | `val1` — тип техники; `val2_from/to` — кубатура; `val3_from/to` — мощность; `val4` — скорости; `val5` — запуск; `val6` — топливо; `val7` — BOM; `val8` — колёса |
| Мотоблоки под заказ | `val3_from/to`, `val4`–`val8` |
| Мотобуксировщики под заказ | `val3_from/to`, `val5`–`val9` |
| Снегоуборщики под заказ | `val2_from/to`, `val3_from/to`, `val4`–`val7` |

| Зимние шины | `val1` — ширина; `val2` — профиль; `val3` — диаметр; `val4` — шипы |

Все эти формы также содержат исходные сортировки: `1` — цена по убыванию, `4` — цена по возрастанию, `2` — название, `3` — дата.

## Реализованный контракт

`catalog-behavior.js` экспортирует `window.MPOINT_CATALOG`:

- `filter(doc, data, options)` применяет точного производителя, доступные `val*`, диапазоны и четыре сортировки. Товары без цены всегда остаются после товаров с числовой ценой. Для `3` восстанавливается исходный порядок.
- `search(query, { index | indexUrl })` лениво загружает компактный `pages/search-index.json` и возвращает товары всех сохранённых категорий. `renderSearch` выводит результат в существующей сетке.
- Достоверные значения фильтров читаются из `options.items[id].filters`, полей item или `data-filter-*` карточки. Неподтверждённые поля возвращаются в `unsupported`; опциональный `sourceFallback` позволяет загрузчику запросить источник. Значения не выводятся из slug или названия товара.
- `sourceRequest` собирает исходный POST из всех полей формы, включая hidden и повторяющиеся значения. Сам модуль запрос не отправляет.
- После загрузки модуль посылает `mpoint:catalog-ready`, после фильтрации — `mpoint:catalog-filtered`.

## Ограничения snapshot и Pages

- В карточках snapshot нет полного набора исходных значений `val*`. Короткий блок `.product-specs` заполнен не у всех товаров и не содержит имён характеристик, поэтому использовать его как универсальный индекс нельзя. Для полного локального паритета extraction должен положить исходные пары фильтра в item metadata или `data-filter-*`; иначе модуль честно сообщает `unsupported` и не исключает товар по догадке.
- В snapshot нет достоверной даты добавления товара; сортировка «по дате» сохраняет серверный исходный порядок.
- Manifest содержит 218 маршрутов, но страницы категорий ссылаются на существенно больше товарных URL, чем сохранено отдельно. Карточки доступны в категориях и участвуют в поиске, однако переход к отсутствующей detail page требует source fallback.
- Среди ссылок категорий отсутствует сохранённый маршрут `/c/mototehnika`. Он ведёт наружу через текущий fallback.
- GitHub Pages не выполняет серверные POST-фильтры, `/catalogue_act.php`, `/popups.php` и другие PHP endpoints. Полный офлайн-режим требует заранее извлечённых данных; отправка реальных заявок в preview не выполняется.

## Визуальный baseline до редизайна

- На ширине 390 px скрывались три пункта навигации, а рейтинги создавали горизонтальную прокрутку.
- На ширине около 838 px телефон обрезался контейнером.
- Поля фильтра имели несогласованные ширины и лишние интервалы.
- Стрелки галереи позиционировались с учётом миниатюр, а `scrollIntoView` вызывал скачки страницы.
- Исходный `index.html` весил около 18,8 MB.
- Загрузка iframe ожидала внешний виджет; UI-обработчики применялись заметно позже первого отображения.

## Подтверждённые сценарии

- На viewport 390 px пункты основной навигации доступны.
- Фильтр производителя Ataki показывает 7 товаров из 83.
- Сортировка цены по убыванию начинается с 244 990 ₽ и далее идёт по убыванию; карточки без числовой цены остаются в конце.
- На товаре с ценой 137 500 ₽ кнопка `+` меняет количество с 2 на 3 и итог на 412 500 ₽.
- Кнопка «Купить» открывает диалог быстрого заказа.
- `node scripts/test-catalog.mjs` проверяет alias `VMC (Vento)`, отсутствие цены, неизменённые начальные диапазоны, явный fallback для изменённого неподдерживаемого диапазона и поиск между категориями по индексу из 4 835 товаров.
